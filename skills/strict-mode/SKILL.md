# Strict Mode

Strict mode strengthens execution of applicable skills. It does not change user intent, expand authority, or add external lifecycle work.

## Obligations

1. Identify applicable skills from clear triggers and read their current instructions before acting.
2. State the intended sequence. Execute dependent steps in order with one active step, while independent work may use another topology.
3. Preserve concrete checkpoints after discovery, implementation, and review so progress and changed assumptions remain visible.
4. Resolve discoverable facts locally. Pause for direction only when an unresolved choice materially affects scope, architecture, safety, or external state.
5. Work in narrow, coherent slices. Use behavioral red-green evidence when valuable, diagnose failures before fixing, and review against correctness, requirements, and repository standards.
6. Before claims, run fresh verification that directly proves them. Report failures, limitations, and incomplete requirements precisely.

For integration-heavy changes, route consequential uncertainty through `clarifying-work`, then use `specifying-work` or `planning-work` when a reviewable contract or dependent sequence is needed. A trivial, well-specified edit does not acquire design ceremony merely because strict mode is active.

## Optional orchestration

Orchestration is separate from strictness. Zellij, Herdr, peers, subagents, and parallel execution remain optional. Use `zellij-agent-herder` only when it is available, requested, and tasks are independent with non-overlapping ownership; otherwise execute sequentially.

When peers are used, give each bounded scope, dependencies, expected output, and verification. Peer reports and output are evidence to verify, not proof of completion. The responsible agent inspects actual changes and performs primary verification before accepting results.

Commits, pull requests, issue trackers, worktrees, releases, and destructive or external actions remain governed by explicit user or repository authority.
