# Agent readiness: requested audit

Use only when asked whether an agent can start and validate a repository from a fresh checkout. This is an observed workflow review, not a generic code-quality score. Set a bounded time and resource budget with the requester or state a reasonable one before trying commands. Avoid destructive setup, automatic fixes, unpinned network scanners, mandatory subagents, and access to live or protected systems. Never print secrets. A blocked path is evidence about that path, not permission to bypass authentication.

1. **Reconstruct a cold start.** Read the README, contributing and agent instructions, toolchain/version files, package scripts, environment examples, and CI entrypoints. Identify the documented bootstrap and run commands, required local services, credentials, and expected success signal. Inspect actual imports, entrypoints, and configuration loading to distinguish an executable path from a stale instruction. Record checkout revision, operating environment, existing dependencies or services, and any other reason this is not a truly clean checkout.
2. **Try the documented path safely.** Within the budget, execute the documented bootstrap and startup when prerequisites and authorization permit. Capture the command, exit status, relevant output, elapsed effort, and observed success signal. If it fails, try a small, justified recovery based on repository evidence and record each inferred step. A lockfile, occupied port, or slow response alone does not prove startup failed. Do not require HTTP when the application does not promise an HTTP endpoint. Mark steps not attempted and why, especially credentials, external services, or account requirements. Do not install dependencies or start services when that would violate the user's boundaries.
3. **Find a small-change feedback loop.** Locate declared test, lint, and type-check commands, then trace their scripts and CI wiring to determine which path actually exercises a representative small change. Run the cheapest valid scoped command when possible, reading its full result. Record scope, duration, actionable failures, noisy output that hides signal, and whether a broader run is necessary. Follow [verifying work](../../verifying-work/SKILL.md) for completion claims. If no usable path exists, diagnose that gap here; construct a reusable harness only when separately requested through `building-verification-harnesses`.
4. **Check documentation against reality.** Compare each claimed setup, startup, and validation step with observed commands and runtime wiring. Distinguish stale instructions, missing prerequisites, genuine failures, and environment-specific blocks. Do not call a path successful just because the README or CI names it. Do not call the repository broken solely because your environment lacks a credential.

Report observed working commands and success signals, corrections or recovery needed, exact friction with file references, blocked or untried paths, and prioritized documentation or workflow fixes. State the tested revision and environment. Separate direct observations from inferred alternatives. No opaque numerical rating, external compatibility scanner, or speculative failure verdict.
