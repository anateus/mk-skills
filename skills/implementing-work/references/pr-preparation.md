# Preparing an authored PR for review

Use this mode when asked to prepare a PR, tidy this PR, clean up commits, annotate the diff, or make an authored change easier to review. Keep reviewer-side evaluation and finding capture in `reviewing-code`. Drafting review guidance does not establish that the change is correct.

1. Identify the exact target from a supplied PR or the current branch, checking its base, head, working tree, commits, changed paths, diff, existing description, and linked issue. Do not assume the branch points to the intended PR. Separate generated or mechanical changes from behavioral logic and note unrelated changes.
2. Compare description claims with the actual diff and fresh checks. Draft a concise account of intent, changed behavior, risk, migration or rollout order, test evidence and gaps, and useful reviewer entry points. Link the real tracker issue when known and say what it delivers; do not invent a ticket or present an unverified check as passing. Explain internal phase references through their source, not just a step number. Prefer plain prose in the author's voice over a template.
3. If the diff remains hard to review, propose a coherent split rather than masking it with notes. Distinguish unfinished work, which warrants a draft PR, from completed work with an external merge gate, which should remain a regular PR with the precise gate and clearing condition noted. Keep later release prerequisites separate from merge gates.
4. For specifically authorized history cleanup, agree on the target commits and intended groupings before rewriting. Record the original head, tree, base, and working-tree state first. Preserve unrelated and uncommitted work. Afterward compare the complete resulting tree with the recorded original, not just the diffstat or apparent size, and inspect any intended differences. Stop if content changed unexpectedly. Never treat a matching diffstat as content identity.

Preparing a draft description or cleanup proposal does not authorize posting, pushing, force-pushing, rebasing, merging, or changing PR state. Obtain separate authorization for those actions, follow repository policy, and do not bypass hooks. Report what was drafted, what was verified, and what still needs approval.
