# Pipeline catalog

Use this catalog when a user asks for a workflow, or when coordinating several agents and a reusable sequence would help. Pick the smallest applicable recipe; do not turn the catalog into a mandatory lifecycle. Each step is a separate skill or source workflow, not a new central runner. This reference ships inside `planning-work` for individual offline installation. Repository paths below are provenance labels, not links or runtime dependencies.

## Authority and selection

- **Local REQUIRED** means an installed skill's own applicable completion/safety condition; it is not a requirement to run every recipe stage. The local planning route selects the smallest applicable set. Skip inapplicable work and state material gaps rather than treating an omitted optional step as failed.
- **Source-required** describes a gate in the named source workflow only. The initial EGM decision rejected mandatory stages, rigid interactive gates and prescribed artifacts as general policy. A later approved review accepted selected adaptations: fresh-context comprehension/readiness perspectives, reader-visible evidence for document feedback, opt-in drift analysis, and this catalog. These local adaptations do not adopt EGM's end-to-end workflow or its external side effects. The EGM workflow itself remains opt-in and applies only when specifically requested.
- A user/repository authority boundary wins over any recipe. Never infer approval for publication, commits, external writes, or destructive changes from a pipeline choice.

## Local software-change recipes

| Step and order | Inputs → outputs | Applicability and gate | Failure / stop behavior | Authority and source |
|---|---|---|---|---|
| Clarify before choosing (optional, first when needed) | Request + repository evidence → settled facts, reversible assumptions, or material unanswered choices | Use only when ambiguity/integration risk could cause substantial rework. Inspect available evidence first; ask only about material choices it cannot settle. | Probe only within authority; label its limits. Stop for a required user decision rather than silently choosing. | Optional local skill `clarifying-work`; repo source `skills/clarifying-work/SKILL.md`, §§Clarify from evidence, Integration scan. |
| Specify behavior (optional, before planning/implementation when a contract is needed) | Agreed intent + evidence → observable behavior, failure behavior, constraints, acceptance criteria, seams, non-goals | Use for specifications, requirements, acceptance criteria, or substantive tracker tickets. Seek approval only for unresolved choices material to scope, architecture, visible behavior, or irreversible work. | Keep assumptions visible; don't create an approval gate for discoverable facts/editorial choices. | Optional local skill `specifying-work`; repo source `skills/specifying-work/SKILL.md`, §§Specification shape, Approval threshold. |
| Plan slices (optional, before dependent multi-step work) | Specification/request + repository evidence → ordered executable slices, owners, dependencies, outputs, verification | Use when steps have dependencies, owned boundaries, or verification points. Discovery/contract proof precedes dependent work; tests stay with behavior. | Review fixed change (risk-based optional) | Fixed base/head or snapshots + specification if present → findings, coverage, residual uncertainty | Use `reviewing-code` for a fixed diff/patch/PR/commit range. ## EGM source-specific workflows (opt-in, not local defaults)

Source: `google/elephant-goldfish-model`, Apache-2.0, reviewed at `7d1b721e51448518cc9b0336465041230200dd10`; mappings are recorded in `config/sources.yaml`. Source-only behaviors below describe that revision, not installed local policy. Later approved decisions adapt selected review concepts; they do not adopt this full source workflow.

| Step and order in EGM | Inputs → outputs | EGM applicability and gate | EGM failure behavior | Local status |
|---|---|---|---|---|
| Brainstorm/alignment → design draft | Concept or notes → agreed concepts brief, then sectioned `design_draft.md` | `skills/egm-draft/SKILL.md` consumes predecessor context, confirms starting context and explicit approval to begin; sections 2–5 have per-section approval gates. Architecture options use an author decision gate. The finished draft is reconciled against the predecessor brief. | Missing predecessor: prompt for context or offer brainstorm; unresolved architectural choice waits for the author. | No EGM draft workflow adopted; local specification and planning gates are independently scoped. Adapted idea: `specifying-work` rereads an earlier brief against the finished draft. |
| Bootstrap contracts (separate documentation task) | Target subtree + repo verification command → leaf/parent README contracts and subtree index | `skills/egm-bootstrap/SKILL.md`: discover/prune tree; more than 15 directories requires explicit scope approval; up to 5 parallel workers with scouts sized by source lines. Scouts cite a file and symbol for each interface instead of inferring from names. | Scout failure yields warning/placeholder and continues; worker failure becomes placeholder link; final verification checks all written contracts/links. | No EGM bootstrap workflow adopted; don't import its directory thresholds, worker caps, generated README requirement, or worker topology. Adapted idea: `analyzing-codebase` does not infer interfaces from file or directory names. |
| Document review preset → staged review | Target doc + optional context + chosen preset → reports/findings | `skills/egm-review/SKILL.md`: explicit preset bypasses preset gate; otherwise select interactive/full report/spec-only/implementation-only. Full interactive order is initial zoom-out → comprehension → critic → intermediate zoom-out → readiness; feature-only omits readiness, implementation-only runs readiness. Interactive stages checkpoint; uninterrupted runs all five. Comprehension starts with a paraphrase and bypasses the synthesizer. | Ambiguous semantic split asks for range; findings route to `egm-resolve`; max-one re-audit and accepted-residual behavior belong to this upstream design only. A failed reviewer is retried once, then recorded as not run. | Adapted ideas: fresh-context comprehension/readiness review with a restatement first, and not-run accounting, in `reviewing-code`. Not adopted: mandatory EGM stages, rigid checkpoints/artifacts, capped re-audit, fixed retry counts, or automatic residual acceptance. |
| Review loop (inside critic and readiness stages) | Target range + reviewers + standards → findings per round, resolved in the author's context | `skills/egm-review-loop/SKILL.md`: fresh reviewers each round; settled findings stay settled, a fixed finding raised again re-opens; converged after two consecutive clean rounds. | Five-round cap or churn asks the user to accept, continue, or return to drafting. | Adapted ideas: settled, re-opened, clean-round and churn rules in `reviewing-code/references/scaling-review.md` and `adversarial-refinement`, with no round constants. |
| EGM-Lite (small changes) | Task → critique, checklist, optional fresh-context spec review, scoped execution, fresh-context diff review, triage | `skills/egm-lite/SKILL.md`: user commands trigger one phase at a time; fixed criteria recommend a spec review; review needs a subagent tool. | Out-of-order command gets a state advisory; missing baseline or uninspectable target reports incomplete coverage instead of approval. | Adapted idea: the fresh-reader level in `reviewing-code`, which discloses a same-context review instead of refusing it. Not adopted: the command state machine, checklist artifacts, or gating criteria. |
| Resolve review findings (only when selected by EGM review) | Target/range + aggregated findings → categorized report and approved edits | EGM categorizes each as contest/escalate/propose-fix/decline; only approved fixes are applied. | Unsupported contests escalate; user can pause/decline; stop for human decision at its interaction gate. | Reader-visible evidence for document feedback is adapted in `handling-review-feedback`; the EGM resolution workflow itself is not adopted. The opt-in drift-audit idea is adapted in `analyzing-codebase`. |
